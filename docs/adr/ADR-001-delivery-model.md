# ADR-001: Выбор гибридной модели поставки (Predictive-Adaptive) для проекта «Практика-Трекер»

- **Статус (Status):** Принято (Accepted)
- **Дата (Date):** 2026-09-22
- **Автор (Author):** Азамат (Solo PM & Developer)
- **Стейкхолдеры (Stakeholders):** Координатор практики ФИТ (внутренний заказчик), преподаватель дисциплины

## 1. Контекст и постановка проблемы (Context and Problem Statement)
Проект «Практика-Трекер» направлен на автоматизацию подачи гарантийных писем и формирования трехсторонних договоров на производственную практику для более 250 студентов ИТ-специальностей ФИТ. Разработка ведется в рамках 15-недельного учебного семестра **одним исполнителем (соло-проект)**.
Управленческое противоречие: С одной стороны, учебный календарь и выпуск приказа деканата привязаны к жестким датам (15 недель семестра, 8-я неделя — РК1, декабрь — дедлайн формирования приказа). С другой стороны, поля форм ввода, автовалидация БИН и шаблон договора требуют постоянного уточнения с координатором практики. Будучи единственным разработчиком, автор несет персональные риски нехватки ресурсов (Bus factor = 1), что исключает любую избыточную бюрократию и требует предельной концентрации на ядре MVP.

## 2. Факторы решения (Decision Drivers)
1. **Неопределенность требований (Средняя):** Базовый сквозной процесс понятен, но детали веб-интерфейса и валидации требуют быстрой доработки по итогам демо с заказчиком.
2. **Стоимость ошибки (Средняя):** Ошибки в договоре задерживают приказ деканата, но не несут финансовых потерь. Допустимо оперативное исправление.
3. **Регуляторика и комплаенс (Средняя):** Требования Закона РК «О персональных данных», разграничение прав доступа.
4. **Вовлеченность заказчика (Периодическая):** Координатор практики доступен для статус-встреч и демонстраций 1 раз в 1-2 недели.
5. **Ресурс разработки (Индивидуальный, 1 человек):** Автор совмещает роли PM, аналитика, разработчика и тестировщика. Коммуникационные потери внутри команды равны нулю, но ресурс ограничен. Неприменимы командные ритуалы Scrum (покер планирования, стендапы с самим собой).
6. **Ограничения бюджета и сроков (Жесткие):** Бюджет 0 тенге (Open Source / Free tier), дедлайн 15 недель не подлежит переносу.

## 3. Рассмотренные альтернативы (Considered Options)
1. **Альтернатива 1: Чистый Waterfall (Предиктивная модель / ГОСТ 34)**
   - *Суть:* Фиксация полного ТЗ на старте, последовательная разработка без промежуточных показов, единая сдача в конце.
   - *Почему отвергнута:* Для одного разработчика изоляция на несколько месяцев ведет к риску построить не то, что нужно координатору, без возможности переделки в конце срока.
2. **Альтернатива 2: Чистый Scrum (Адаптивная модель)**
   - *Суть:* Итеративная разработка без фиксированных дат релиза, классические командные церемонии.
   - *Почему отвергнута:* Scrum разработан для команд от 3 до 9 человек. Для одного исполнителя командные церемонии превращаются в фикцию, а плавающие сроки релиза недопустимы из-за приказа деканата в декабре.
3. **Альтернатива 3: Гибридная модель (Predictive Milestones + Adaptive 2-week Solo Sprints)**
   - *Суть:* Внешний контур проекта зафиксирован вехами семестра (недели 4, 8, 11, 15). Внутренний контур разработки строится по принципу персонального канбана (Personal Kanban) и 2-недельных спринтов с автоматизацией контроля качества (CI/CD, линтеры) вместо ручного ревью.

## 4. Решение (Decision Outcome)
**Выбрана Альтернатива 3: Гибридная модель поставки.**
Проект управляется предиктивно на уровне академических вех семестра, а разработка ведется 2-недельными итерациями одним разработчиком с жестким контролем объема MVP.

## 5. Последствия решения и компромиссы (Consequences & Trade-offs)
- **Положительные последствия:**
  - Нулевые накладные расходы на согласования внутри команды (быстрое принятие технических решений).
  - 100% гарантия удержания дедлайна семестра за счет фокуса только на ядре продукта.
  - Регулярная обратная связь от координатора практики каждые 2 недели.
- **Отрицательные последствия и риски:**
  - Высокий персональный риск (Bus factor = 1): при болезни или задержке подменить разработчика некому.
  - Отсутствие второго человека для Code Review компенсируется строгим чек-листом самопроверки и автотестами.
- **Меры митигации рисков:**
  - Радикальный де-скоупинг по MoSCoW: Must Have (авторизация, заявка, генерация договора) делаются в первую очередь. Любой второстепенный функционал отсекается.
  - Настройка автоматических проверок (линтер flake8, pytest) в pre-commit и GitHub Actions.
