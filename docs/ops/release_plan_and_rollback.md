## 1. Регламент и окна релизов (Release Windows & Freeze Policy)

Для минимизации риска прерывания работы деканата и 250+ студентов в проекте установлены строгие временные рамки доставки обновлений:

| Параметр | Установленный норматив | Обоснование |
| :--- | :--- | :--- |
| **Плановые окна релизов** | **Вторник и Четверг с 01:00 до 04:00 (GMT+5)** | Период нулевой пользовательской активности студентов и сотрудников деканата |
| **Срочные хотфиксы (P1/P2)** | В любое время после локальной верификации и прогона CI | Критические уязвимости безопасности или блокировка сдачи договоров практики |
| **Запрет релизов (Release Freeze)** | **Пятница после 15:00, суббота, воскресенье** | Исключение риска возникновения дежурных инцидентов в нерабочее время вуза |
| **Академический мораторий** | Неделя массовой защиты отчетов практики (середина июля) | Замораживание любых обновлений функционала во избежание срыва аттестации |

## 2. Чек-лист готовности к релизу (Pre-Release Checklist)

Перед развертыванием новой версии в боевом окружении solo-разработчик обязан подтвердить следующие условия:

- [ ] **1. Статус пайплайна:** Все 4 джобы GitHub Actions (`lint`, `test`, `security`, `build`) имеют статус `Success` в ветке `main`.
- [ ] **2. Тестовое покрытие:** Покрытие кода тестами превышает 60% (фактически 96.95%, отчет `coverage.xml` сохранен).
- [ ] **3. Бекап базы данных:** Создан свежий моментальный снимок рабочей БД PostgreSQL:
  ```bash
  docker compose exec -T db pg_dump -U praktika_user -d praktika_db | gzip > /opt/backups/praktika_db_$(date +%Y%m%d_%H%M%S).sql.gz
  ```
- [ ] **4. Миграции Alembic:** Скрипты миграций предварительно протестированы на локальном дампе рабочей БД в режиме `alembic upgrade head` и проверена обратимость `alembic downgrade -1`.
- [ ] **5. Информирование пользователей:** В Telegram-канале деканата размещено предупреждение о плановом техническом обслуживании за 4 часа до окна.

## 3. Пошаговый сценарий планового развертывания (Deployment Runbook)

```bash
# Шаг 1. Переход в директорию сервиса на сервере PS.kz
cd /opt/praktika-tracker

# Шаг 2. Загрузка последнего проверенного состояния ветки main
git fetch origin main
git checkout main
git pull origin main

# Шаг 3. Сборка нового продакшен-образа
docker compose build --pull app

# Шаг 4. Применение миграций схемы базы данных
docker compose run --rm app alembic upgrade head

# Шаг 5. Перезапуск веб-сервиса с нулевым простоем (Graceful Reload)
docker compose up -d --no-deps --remove-orphans app

# Шаг 6. Валидация работоспособности (Smoke Test)
curl -f http://localhost:8000/healthz || exit 1
```

## 4. План аварийного отката (Emergency Rollback Runbook)

При возникновении сбоя (Healthcheck отвечает `5xx`, сбой валидации БИН, повреждение структуры договоров) активируется сценарий отката. **Целевой норматив MTTR: менее 20 минут.**

### Шаг 1. Определение точки отката
Определить хеш предыдущего стабильного коммита:
```bash
git log --oneline -n 5
# Пример: стабильный коммит — d75a793, сбойный — HEAD
PREV_STABLE_HASH=$(git rev-parse HEAD~1)
```

### Шаг 2. Откат схемы базы данных (Database Rollback)
Если сбойный релиз содержал изменение схемы БД:
```bash
# Вариант А: Быстрый откат на 1 миграцию назад через Alembic
docker compose run --rm app alembic downgrade -1

# Вариант Б: При нарушении целостности данных — аварийное восстановление из бекапа
gunzip < /opt/backups/praktika_db_LATEST.sql.gz | docker compose exec -T db psql -U praktika_user -d praktika_db
```

### Шаг 3. Откат контейнера приложения (Container Rollback)
```bash
# Переключение на стабильный коммит в Git
git checkout $PREV_STABLE_HASH

# Перезапуск контейнера на базе проверенного кода
docker compose up -d --build --force-recreate app

# Проверка статуса контейнеров
docker compose ps
docker compose logs --tail=50 app
```

### Шаг 4. Проверка доступности системы (Post-Rollback Healthcheck)
```bash
# Проверка эндпоинта здоровья
curl -s http://localhost:8000/healthz | jq .

# Проверка эндпоинта валидации ключевого сервиса БИН
curl -s -X POST http://localhost:8000/api/v1/bin/validate \
  -H "Content-Type: application/json" \
  -d '{"bin": "081240012740"}' | jq .
```

### Шаг 5. Постмортем и фиксация инцидента
1. Внести запись об инциденте в `docs/ops/incidents.md` с указанием причины сбоя, продолжительности простоя и мер по предотвращению повторения.
2. Сформировать тикет в бэклоге со статусом `P1-Bugfix` для доработки тестового покрытия.
