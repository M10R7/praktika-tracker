## 1. Концепция качества как управленческой функции

В рамках проекта «Практика-Трекер» обеспечение качества (Quality Assurance) рассматривается не как изолированная финальная фаза ручной проверки перед сдачей, а как **сквозной управленческий процесс**, интегрированный во все стадии жизненного цикла разработки ПО.

### 1.1 Модель стоимости дефекта (Defect Cost Amplification)
Стоимость устранения дефекта экспоненциально возрастает по мере продвижения по стадиям жизненного цикла:
- **Фаза анализа требований:** обнаружение неоднозначности в алгоритме проверки БИН стоит **1x** (исправление формулировки в User Story);
- **Фаза проектирования и архитектуры:** перепроектирование схемы БД при выявлении отсутствия уникального ключа на уровне моделей стоит **5x**;
- **Фаза модульной и интеграционной разработки:** исправление бага на этапе Unit/Integration тестов стоит **10x**;
- **Фаза приемочных испытаний (UAT):** возврат релиза заказчиком из-за некорректного формата DOCX стоит **25x**;
- **Фаза промышленной эксплуатации (Production):** отзыв неверно сформированного приказа деканата, паралич распределения 250 студентов и скандал с работодателями стоит **100x+** (включая репутационные потери факультета и штрафные санкции).

### 1.2 Система контрольных шлюзов качества (Quality Gates)

| Шлюз | Фаза процесса | Ответственный | Входные критерии (DoR) | Выходные критерии (DoD) | Действие при несоответствии |
|---|---|---|---|---|---|
| **QG-1: Backlog Gate** | Спринт-планирование | Solo PM (Азамат) | Наличие User Story по INVEST | Наличие критериев приемки (AC), схемы валидации и макета | Задача не берется в разработку (Discard / Refine) |
| **QG-2: Commit Gate** | Локальная разработка | Solo Dev (Азамат) | Написанный код фичи | Пройден pre-commit хук: Ruff 0 ошибок, Pyright/MyPy чист | Коммит отклоняется git hook |
| **QG-3: CI Pipeline Gate** | Pull Request / Merge | GitHub Actions CI | Открытый PR в `main` | 100% passing тестов pytest, Coverage $\ge 80\%$, успешный build Docker | Блокировка мерджа (Branch Protection) |
| **QG-4: UAT & Release Gate** | Поставка инкремента | Заказчик (Координатор ФИТ) | Развернутый Staging стенд | 100% пройденных UAT-сценариев, подписан протокол приемки, 0 дефектов Block/Critical | Релиз блокируется, дефекты вносятся в топ бэклога |

## 2. Пирамида тестирования и уровни верификации

Стратегия базируется на классической трехуровневой пирамиде тестирования Майка Кона с дополнением верификации нефункциональных требований (НФТ):

```
               /\
              /  \     Приемочные тесты и UAT (5 сценариев)
             / UAT\    Ручная верификация бизнес-сценариев деканата
            /------\
           /        \   Интеграционные тесты API (11 тестов)
          /Integration\ Эндпоинты FastAPI, TestClient, транзакции БД
         /--------------\
        /                \  Unit-тесты бизнес-логики (38 тестов)
       /    Unit Tests    \ Алгоритмы КГД РК (ИИН/БИН), генераторы DOCX/CSV
      /--------------------\
```

### 2.1 Уровень 1: Unit-тестирование (Компонентные тесты)
- **Объект тестирования:** изолированные сервисные функции без внешних зависимостей.
- **Ключевые наборы тестов:**
  1. `tests/test_iin_validator.py` (21 тест): математическая валидация контрольного разряда ИИН РК с двумя весовыми массивами $W_1$ и $W_2$, проверка корректности даты рождения (включая високосные года) и пола/века (диапазон цифр 1–6).
  2. `tests/test_bin_validator.py` (11 тестов): проверка 12-значного БИН юридических лиц, типов организаций (4, 5, 6) и корректности контрольной суммы.
  3. `tests/test_contract_service.py` (5 тестов): генерация уникальных номеров договоров по маске, верификация матрицы допустимых переходов конечного автомата состояний (`draft` $\rightarrow$ `under_review` $\rightarrow$ `approved` $\rightarrow$ `in_order` / `rejected`).
- **Среда и изоляция:** выполняется в памяти через `pytest`, запуск занимает $< 1.5$ сек.

### 2.2 Уровень 2: Интеграционное тестирование API
- **Объект тестирования:** взаимодействие REST-контроллеров FastAPI, ORM SQLAlchemy, сессий SQLite/PostgreSQL и файловой системы.
- **Ключевые наборы тестов (`tests/test_api_endpoints.py`, `tests/test_mvp_workflow.py`):**
  - Проверка сквозных HTTP-запросов через `fastapi.testclient.TestClient`.
  - Валидация входных Pydantic схем и корректность HTTP кодов (200, 201, 400, 404, 409, 422).
  - Проверка контроля уникальности (защита от повторной подачи заявки одним студентом, предотвращение дублирования номеров приказов с кодом 409 Conflict).
  - Верификация бинарных потоков: скачивание DOCX-договора и DOCX-приказа (проверка MIME-типа и сигнатуры архива `PK\x03\x04`), скачивание CSV с UTF-8 BOM (`\xef\xbb\xbf`).
  - Проверка загрузки скан-копий договоров (Multipart form-data) и валидации допустимых расширений (PDF, JPG, PNG).

### 2.3 Уровень 3: Сквозное и приемочное тестирование (E2E & UAT)
- **Объект тестирования:** целостные пользовательские сценарии взаимодействия через веб-интерфейс (Jinja2 + Bootstrap 5 + Vanilla JS).
- **Сценарии:** пошаговое прохождение жизненного цикла студенческой заявки от заполнения веб-формы до скачивания утвержденного приказа.

### 2.4 Уровень 4: Тестирование нефункциональных требований (НФТ)
1. **Нагрузочное тестирование (Performance & Load):**
   - Инструмент: `k6` (скрипт `tests/load/k6_test.js`).
   - Нагрузочный профиль: 250 виртуальных пользователей (Virtual Users — VUs) в течение 10 минут (имитация дедлайна сдачи заявок).
   - Критерии приемки: P95 Latency $\le 300$ мс, уровень ошибок HTTP $0.0\%$, пропускная способность $\ge 150$ req/s.
2. **Информационная безопасность и защита ПДн (Security & Privacy):**
   - Проверка защиты от массового перебора ИИН через публичный трекер (`/tracker`): лимит SlowAPI 15 запросов в минуту с одного IP, при превышении возврат HTTP 429 Too Many Requests (`SEC-01`).
   - Проверка маскирования персональных данных (ФИО `Сәбитов А. Б.`, ИИН `030514******`, скрытие телефонов и email посторонним лицам).
   - Проверка неизменяемости журнала аудита статусов (`SEC-02`): запрет операций UPDATE и DELETE для таблицы `status_audit_logs`.
3. **Локализация и мультиязычность (i18n):**
   - Верификация переключения языкового контекста (RU / KZ) на всех страницах портала (`НФТ-10`).

## 3. Политика управления тестовыми данными

1. **Синтетический детерминированный датасет:**
   - Генерация валидных контрольных сумм по алгоритму КГД МФ РК для исключения использования реальных персональных данных живых людей на тестовых стендах.
   - 7 эталонных предприятий РК (BTS Digital, Kaspi, Казахтелеком, Halyk, NITEC и др.) с реальными публичными БИН.
2. **Обезличивание данных (Data Masking) при миграции:**
   - При создании дампов из продуктивной среды ФИО студентов маскируются по маске «Студент_№XXXX», ИИН генерируются заново с сохранением валидного контрольного разряда, контактные телефоны заменяются на диапазон `+7 (700) 000-00-XX`.
