## 1. Спецификация сценариев приемочного тестирования (UAT Test Cases)

### Сценарий UAT-01: Первичная подача заявления студентом с выбором аккредитованной базы практики
- **Трассировка:** US-01, US-04, WBS 1.3.1
- **Предусловия:** Студент открыл страницу `/apply`, в базе имеется аккредитованная компания ТОО «BTS Digital» (БИН `180540018590`).
- **Шаги выполнения:**
  1. Заполнить ФИО: «Сәбитов Азамат Ерланович».
  2. Ввести валидный ИИН: `030514500012`.
  3. Ввести корпоративную почту: `azamat.sabitov@enu.kz` и телефон `+7 (707) 812-44-55`.
  4. Выбрать группу «АЖ-47» и специальность «6B06101 - Информационные системы».
  5. В режиме «Выбрать из партнеров» указать «ТОО «BTS Digital»» (БИН подставится автоматически с зеленой галочкой).
  6. Указать руководителя от предприятия и нажать кнопку «Подать заявление».
- **Ожидаемый результат:** Система валидирует поля, выводит всплывающее уведомление (Toast) зеленого цвета с номером заявки вида `ПР-2026-FIT-XXXX`, форма сбрасывается, в БД создается запись со статусом `under_review`.
- **Фактический результат:** Заявка успешно зарегистрирована за 180 мс, номер присвоен, всплывающий Toast отобразился корректно.
- **Статус:** **Passed (Пройден)**

### Сценарий UAT-02: Обработка некорректного БИН организации при попытке ручного ввода
- **Трассировка:** US-04, NFR ISO 25010 (Reliability)
- **Предусловия:** Открыта страница `/apply`, активирован радиобаттон «Ввести свою организацию».
- **Шаги выполнения:**
  1. Заполнить валидные личные данные студента.
  2. В поле «БИН организации» ввести `123456789012` (контрольная сумма математически не сходится с алгоритмом КГД РК).
  3. Перевести фокус на следующее поле (событие `onblur`).
- **Ожидаемый результат:** Поле подсвечивается красной рамкой, под полем выводится ошибка: «Несовпадение контрольного разряда БИН по алгоритму КГД РК», кнопка отправки формы блокируется.
- **Фактический результат:** Алгоритмический валидатор на клиенте и сервере мгновенно заблокировал ошибочный БИН, отправка невозможна.
- **Статус:** **Passed (Пройден)**

### Сценарий UAT-03: Защита от повторной подачи активной заявки одним обучающимся
- **Трассировка:** US-01, SEC-03, Integrity Rules
- **Предусловия:** В системе уже существует активная заявка от студента с ИИН `030514500012`.
- **Шаги выполнения:**
  1. Заполнить форму `/apply` повторно с тем же ИИН `030514500012`, но указав другую компанию (АО «Kaspi Bank»).
  2. Нажать кнопку «Подать заявление».
- **Ожидаемый результат:** Запрос отклоняется сервером с HTTP кодом 400 Bad Request. Пользователю выводится понятное сообщение: «По данному ИИН уже зарегистрирована активная заявка со статусом '...'. Повторная подача отклонена».
- **Фактический результат:** Сервер предотвратил дублирование, вывел понятный алерт с номером имеющейся заявки.
- **Статус:** **Passed (Пройден)**

### Сценарий UAT-06: Отклонение некорректной заявки с обязательным указанием причины отказа
- **Трассировка:** US-06, WBS 1.3.2, Audit Trail
- **Предусловия:** В кабинете `/coordinator` отображается заявка студента Нұрланұлы Б.
- **Шаги выполнения:**
  1. Нажать кнопку красного цвета с иконкой крестика («Отклонить»).
  2. В открывшемся модальном окне оставить текстовое поле пустым и нажать «Подтвердить отклонение».
  3. Проверить валидацию.
  4. Ввести обоснованную причину: «Несоответствие профиля деятельности компании учебной программе специальности 6B06102» и подтвердить.
- **Ожидаемый результат:** Без ввода причины система не позволяет отправить запрос (HTML5 required + API 422 Unprocessable Content). После ввода причины статус меняется на `rejected`, в аудит-логе фиксируется причина и автор действия. В публичном трекере студент видит понятное пояснение отказа.
- **Фактический результат:** Модальное окно принудительно затребовало причину, аудит-лог зафиксировал комментарий координатора.
- **Статус:** **Passed (Пройден)**
