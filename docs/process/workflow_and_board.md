### 1. Структура колонок канбан-доски и WIP-лимиты

В условиях индивидуальной разработки ограничение незавершённой работы (Work in Progress, WIP) является ключевым инженерным рычагом борьбы с переключением контекста (Context Switching) и деградацией пропускной способности.

| Колонка доски | Назначение колонки | WIP (Спринт 1) | WIP (Спринт 2) | Обоснование изменения WIP |
|---|---|---|---|---|
| **1. Product Backlog** | Приоритизированный перечень требований (User Stories / Tech Tasks) | $\infty$ | $\infty$ | Стратегический пул задач проекта. |
| **2. Ready for Dev** | Задачи, полностью удовлетворяющие критериям Definition of Ready | 3 | 3 | Очередь ближайших задач на 2–3 рабочих дня. |
| **3. In Progress** | Активная разработка (написание кода FastAPI, вёрстка, миграции) | **3** *(ошибка)* | **1** *(фокус)* | **Принцип «Stop Starting, Start Finishing»**: solo-разработчик работает строго над одной задачей за раз. |
| **4. In Review / Test** | Локальный прогон автотестов pytest, линтинг ruff, проверка критериев приёмки | **2** | **1** | Защита от накопления «почти готовых» задач; немедленная доводка до Done. |
| **5. Done** | Завершённые инкременты, удовлетворяющие критериям Definition of Done | $\infty$ | $\infty$ | Поставленный результат, готовый к демонстрации и релизу. |

### 2. Явные политики перехода между статусами (Explicit Policies)

1. **Backlog $\rightarrow$ Ready for Dev**:
   * Задача декомпозирована до размера не более 5 Story Points (или до 1.5 дней разработки);
   * Зафиксированы критерии приёмки Given–When–Then (BDD);
   * Проверено отсутствие внешних блокирующих зависимостей (шаблоны, доступы).
2. **Ready for Dev $\rightarrow$ In Progress**:
   * Переход разрешён **только если в колонке In Progress освободился слот** (текущий WIP = 0);
   * Разработчик создаёт тематическую ветку Git по стандарту `feat/ISS-<номер>-<краткое-название>` от актуального `main`.
3. **In Progress $\rightarrow$ In Review / Test**:
   * Код написан, локально пройдены проверки форматирования (`ruff check .`);
   * Написаны модульные тесты для новой бизнес-логики;
   * Выполнен локальный запуск сервера, базовый позитивный сценарий проверен вручную.
4. **In Review / Test $\rightarrow$ Done**:
   * 100% автотестов в pytest выполняются успешно без падений (`pytest -q`);
   * Сформирован Pull Request в репозитории `praktika-tracker`;
   * Выполнен коммит по стандарту Conventional Commits (`feat: ...`, `fix: ...`);
   * Проверено выполнение всех критериев приёмки из карточки задачи;
   * Документация (Swagger/OpenAPI или Markdown) актуализирована при изменении API.

### 3. Определение готовности к разработке (Definition of Ready, DoR)

Задача допускается к перемещению в колонку **Ready for Dev** только при одновременном выполнении следующих 5 условий:
1. **Ясная бизнес-цель**: сформулирован пользовательский сценарий по шаблону: *«Как [роль], я хочу [действие], чтобы [бизнес-ценность]»*;
2. **Критерии приёмки (Acceptance Criteria)**: прописаны не менее 2 сценариев (позитивный и негативный) в формате *Дано — Когда — Тогда*;
3. **Оценка размера**: задача оценена по шкале Фибоначчи и имеет размер **S (2 SP)** или **M (3–5 SP)**. Задачи размера L (8+ SP) декомпозируются;
4. **Технические артефакты**: определены сигнатуры HTTP-методов (эндпоинт, DTO схемы Pydantic) и затронутые таблицы СУБД;
5. **Отсутствие блокеров**: для задачи доступны все необходимые внешние данные (утверждённые образцы формул, шаблоны Word).

---

### 4. Определение завершённости (Definition of Done, DoD)

Задача признаётся полностью завершённой (**Done**) только при соблюдении 6 обязательных инженерных критериев:
1. **Код завершён**: функционал полностью реализован в соответствии со спецификацией;
2. **Автотесты написаны и пройдены**: новые функции покрыты модульными/интеграционными тестами pytest, тестовое покрытие кодовой базы не снизилось;
3. **Статический анализ чист**: проверки `ruff` и `flake8` завершаются с кодом возврата 0 (отсутствуют синтаксические и стилистические ошибки);
4. **Безопасность проверена**: в коде отсутствуют захардкоженные пароли, токены и секреты (верификация Gitleaks);
5. **Ветка влита в main**: изменения слиты в основную ветку репозитория через Pull Request без конфликтов;
6. **Критерии приёмки подтверждены**: все Given–When–Then условия продемонстрированы на локальном стенде разработчика.
