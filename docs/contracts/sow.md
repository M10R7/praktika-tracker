### 1. Предмет соглашения и назначение системы

Настоящий Statement of Work (SoW) определяет цели, границы, состав результатов, процедуру приёмки, порядок управления изменениями и права на интеллектуальную собственность при разработке, развёртывании и вводе в опытную эксплуатацию веб-сервиса **«Практика-Трекер»**.

**Назначение системы**: Автоматизация процесса распределения студентов 3–4 курсов ФИТ (более 250 обучающихся) на производственную и преддипломную практику, включая:
1. Подачу онлайн-заявок студентами с алгоритмической верификацией реквизитов баз практики (проверка БИН по алгоритму КГД РК);
2. Ведение единого общекафедрального справочника аккредитованных организаций-партнёров;
3. Двустороннюю координацию: согласование/отклонение заявок ответственным координатором кафедры с фиксацией истории статусов;
4. Серверную автоматическую генерацию типовых трёхсторонних договоров в форматах DOCX и PDF в соответствии с типовой формой Приказа МОН РК № 107;
5. Автоматизированное формирование сводного проекта приказа деканата о направлении студентов на практику с группировкой по организациям;
6. Публичный мониторинг статуса прохождения документов по ИИН обучающегося без необходимости авторизации.

### 3. Границы проекта (Project Scope Boundaries)

#### 3.1. В границах проекта (In-Scope — MVP)
* Реализация пользовательских историй приоритета MVP: US-01, US-02, US-03, US-04, US-05, US-06, US-07, US-09, US-10, US-11, US-12, US-14;
* Обработка данных потока численностью до 500 студентов и до 100 профильных баз практики;
* Автоматическая валидация 12-значного БИН с вычислением контрольного разряда (алгоритм весовых коэффициентов);
* Генерация документов DOCX с динамическим заполнением реквизитов сторон;
* Генерация сводного приказа деканата с автоматической сортировкой организаций по алфавиту и исключением неподтверждённых студентов в отдельный список;
* Развёртывание на Cloud VPS хостинг-провайдера в юрисдикции Республики Казахстан (PS.kz, г. Алматы) с подключением SSL-сертификата Let's Encrypt.

#### 3.2. За рамками проекта (Out-of-Scope — Версии 2 и 3)
* Разработка нативных мобильных приложений для операционных систем iOS и Android (заменено адаптивной мобильной вёрсткой веб-интерфейса);
* Полнофункциональный личный кабинет студента с авторизацией и 4-летним архивом (US-15 перенесена в релиз 2.0);
* Прямая двухсторонняя интеграция по закрытому REST API с АИС «Platonus» (US-18 перенесена в релиз 3.0, на этапе MVP обмен осуществляется через унифицированный Excel/CSV импорт);
* Интеграция с сервисом цифровой подписи ЭЦП НУЦ РК (договоры формируются для печати и последующего подписания физическими печатями предприятий);
* Модуль распознавания сканированных копий (OCR) на базе машинного обучения.

### 4. Порядок приёмки и критерии оценки качества (Acceptance Criteria)

Приёмка результатов проекта осуществляется комиссией в составе:
1. Заместитель декана ФИТ по учебной работе (Председатель);
2. Ответственный координатор производственной практики кафедры ИС;
3. Ведущий разработчик / Solo PM (Сәбитов А.).

#### 4.1. Этапы приёмочных испытаний
1. **Автоматизированная верификация**: Успешное выполнение пайплайна GitHub Actions (тесты pytest пройдены на 100%, тестовое покрытие строк кода $\ge 80\%$, отсутствие критических уязвимостей в Trivy/Gitleaks);
2. **Нагрузочное тестирование**: Подтверждение целевых нефункциональных требований инструментом k6 (время ответа p95 $\le 1.0$ с при 30 виртуальных пользователях, отсутствие HTTP 5xx ошибок);
3. **Пользовательские приёмочные испытания (UAT)**: Выполнение сквозных сценариев реальными пользователями:
   * Студент подаёт заявку с реальным БИН предприятия $\rightarrow$ система корректно валидирует номер;
   * Координатор одобряет заявку $\rightarrow$ статус обновляется в реальном времени;
   * Генерация договора $\rightarrow$ реквизиты студента, вуза и компании подставлены без искажения структуры бланка;
   * Генерация приказа $\rightarrow$ 250 записей сгруппированы корректно за время $\le 3.5$ с.

#### 4.2. Формализация приёмки
При отсутствии блокирующих (Severity 1) и критических (Severity 2) дефектов Заказчик подписывает двусторонний **Акт приёма-передачи результатов опытной эксплуатации** в течение 5 (пяти) рабочих дней с даты проведения демонстрации.

### 5. Порядок внесения изменений (Change Management Procedure)

Для предотвращения неконтролируемого разрастания скоупа (Scope Creep) устанавливается следующий регламент:
1. Любое требование, выходящее за рамки таблицы раздела 3.1, оформляется Заказчиком в виде официального **Change Request (CR)** через трекер GitHub Issues с обязательными полями: обоснование бизнес-ценности, ожидаемый результат, критерии приёмки;
2. Исполнитель выполняет оценку влияния запроса (Impact Analysis) в течение 3 рабочих дней: рассчитывается трудоёмкость в часах/Story Points, влияние на дату итоговой сдачи и архитектурные риски;
3. **Принцип нулевой суммы скоупа (Zero-Sum Scope)**: Принятие нового требования трудоёмкостью более 8 человеко-часов требует пропорционального исключения (дескоупинга) функциональности эквивалентного объёма из текущего релиза с переносом в следующий релиз;
4. Окончательное решение принимается совместным протоколом Управляющего комитета. Устные согласования юридической и технической силы не имеют.
