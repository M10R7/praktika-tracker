## 1. Контекст соло-разработки и архитектурное обоснование

При реализации проекта силами одного разработчика (solo developer & PM) классическая модель коллегиального код-ревью (*Peer Code Review*) не применима физически. Попытки имитировать ревью от вымышленных участников приводят к девальвации инженерных процессов. 

Вместо коллегиального утверждения в проекте «Практика-Трекер» развернута строгая система **автоматизированных контрольных барьеров (Automated Quality Gates)** на базе CI/CD GitHub Actions и формализованного **Self-Review Checklist**. Это гарантирует предотвращение регрессий, утечки секретов и попадания нестабильного кода в ветку `main`.

## 2. Конфигурация GitHub Branch Protection Rules для ветки `main`

В настройках репозитория (`Settings` -> `Branches` -> `Branch protection rules` -> `Branch name pattern: main`) активированы следующие обязательные директивы:

### 2.1. Запрет прямой отправки коммитов (Direct Push Prohibited)
* **Параметр:** `Require a pull request before merging` — включен.
* **Пояснение:** Прямые коммиты (`git push origin main`) заблокированы на уровне сервера. Вся разработка ведется в тематических ветках:
  * `feature/<ticket-id>-<short-description>` (новая функциональность);
  * `fix/<ticket-id>-<short-description>` (исправление дефекта);
  * `refactor/<short-description>` (рефакторинг);
  * `chore/<short-description>` (обновление конфигурации и пайплайнов).

### 2.2. Обязательные проверки статуса (Require Status Checks to Pass)
* **Параметр:** `Require status checks to pass before merging` — включен;
* **Параметр:** `Require branches to be up to date before merging` — включен (Strict Merge Policy).
* **Обязательные CI-задачи (Mandatory Status Checks):**
  1. `Lint & Code Style (Ruff)` — статический анализ кода, соответствие PEP 8, проверка импортов;
  2. `Unit & Integration Tests (pytest)` — прохождение 100% модульных и интеграционных тестов с минимальным порогом покрытия кода тестами `--cov-fail-under=60` (текущий фактический показатель: 96.95%);
  3. `Security & Secret Scan (Gitleaks & Trivy)` — сканирование истории коммитов на наличие утекших API-токенов, паролей БД, а также сканирование уязвимостей (CVE) сторонних зависимостей;
  4. `Docker Container Build` — успешная многоэтапная сборка легковесного контейнера на базе `python:3.11-slim-bookworm` без предупреждений безопасности.

### 2.3. Линейная история коммитов (Linear History Enforcement)
* **Параметр:** `Require linear history` — включен.
* **Пояснение:** Исключаются «мерж-узлы» (`merge commits`) с двумя родителями. Вливание изменений в `main` осуществляется исключительно через **Squash and Merge** или **Rebase and Merge**. Это обеспечивает кристальную читаемость истории коммитов, упрощает вычисление DORA-метрик и делает операцию отката (`git revert`) тривиальной.

### 2.4. Запрет деструктивных операций
* **Параметр:** `Do not allow force pushes` — включен для всех, включая администратора репозитория.
* **Параметр:** `Do not allow deletions` — включен (удаление ветки `main` аппаратно невозможно).

## 3. Регламент и чек-лист самопроверки (Solo Self-Review Checklist)

Перед слиянием Pull Request в ветку `main` разработчик обязан последовательно верифицировать следующие пункты:

1. **Трассируемость задачи:** В заголовке и описании PR присутствует ссылка на задачу из проектного бэклога (например, `fit-core-10: CI/CD Pipeline & DORA`).
2. **Локальный зеленый статус:** Локально выполнены команды:
   * `pytest -v --cov=src --cov-fail-under=60` — все тесты пройдены без ошибок;
   * `ruff check .` — отсутствуют предупреждения линтера;
   * `docker-compose config` — синтаксис манифестов контейнеризации валиден.
3. **Безопасность:**
   * Проверено отсутствие жестко закодированных секретов (`DATABASE_URL`, токены деканата) в кодовой базе; все параметры считываются из `.env` через `pydantic.BaseSettings`.
   * Контейнер Dockerfile выполняется от имени непривилегированного пользователя `appuser (uid=1001)`.
4. **Миграции и обратная совместимость:**
   * Если затронута схема БД, подготовлена обратимая миграция Alembic (`upgrade` и `downgrade`).
5. **DORA-мониторинг:**
   * Каждый коммит имеет валидный формат *Conventional Commits* (`feat:`, `fix:`, `refactor:`, `test:`, `chore:`) для корректной работы алгоритма автоматического анализа DORA-метрик.
